# Producer app checkpoint

This checkpoint intentionally groups accumulated work across authentication, the API client, community and discovery screens, license-related interface metadata, protected previews, quality checks, and deployment configuration. It is a repository-state checkpoint, not a preview-only change set.

## Deployment workflow

The removed `.github/workflows/main_beatnow.yml` was the former Azure Web App deployment workflow. It built the app and deployed to Azure Web App `beatnow` using a GitHub Actions publish-profile secret reference. This replacement makes Vercel the deployment target: Vercel builds the Vite SPA from `vercel.json`, while `.github/workflows/quality.yml` runs lint, tests, build, and artifact scanning on pushes and pull requests. This checkpoint does not push or deploy; create a PR and verify the Vercel preview before merging.

## Repository hygiene review

The previously tracked `vite.config.ts.timestamp-1715615716968-670de4b08d3de.mjs` was generated by Vite and embedded a source map with an absolute developer-machine path, so it is removed from this checkpoint. Earlier Git objects are left intact; this commit does not rewrite history. The older deleted Firebase demo configuration contains a Firebase web API key. Firebase documents these keys as public project identifiers rather than authorization secrets; keep Firebase Security Rules/App Check and API restrictions in force. No private keys, access tokens, passwords, or credential-bearing service URLs were found in the current changes. Development loopback URLs are confined to local documentation/test fixtures, and `.env.example` leaves the proxy value empty.

## Backend contract dependencies

- Beat APIs should return `processing_status` (`processing`, `ready`, or `failed`) and `preview_url`. `audio_url` is accepted only as the migration fallback.
- Upload accepts optional `preview_start` and `preview_end` values and returns the resulting beat state. The UI reports publication success only for `ready` with a preview URL.
- The web session flow uses the web-specific refresh endpoint and in-memory access-token handling; authentication routes and cookie behavior must be available in the deployed backend.
- Analysis-based upload continues to depend on the existing analysis API and its publish-from-analysis route. No preview polling route is assumed.
